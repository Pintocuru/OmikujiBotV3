# ルート README・構成ドキュメント整備プロンプト

以下を AI エージェントへの依頼文として使用する。

---

このリポジトリのルート README と開発者向け構成ドキュメントを、実装に基づいて整備してください。

対象リポジトリ: `Pintocuru/OmikujiBotV3`

## 最重要ルール

- コードが読めない場合は、他の作業を一切せず「読めませんでした」とだけ返して中止すること。
- 最初に `AGENTS.md` と `docs/conventions/` を読むこと。
- `docs/conventions/root-readme.md` を本作業のルールとする。
- 実装を確認せずに、ファイル名・ディレクトリ名から仕様を推測しないこと。
- 未確認の内容は「未確認」とし、事実のように書かないこと。
- アプリケーションコード、設定、ビルド処理の変更は禁止。ドキュメントだけを変更すること。
- commit / push はしないこと。変更は patch で提出すること。

## 目的

ルートの `README.ja.md` をプロジェクト全体の概要・入口として整理し、各項目の詳細を `docs/architecture/` 以下の Markdown に分離する。

## 作業手順

### 1. 現状調査

- `README.ja.md` の各項目とディレクトリ一覧を確認する。
- 対応する実装、エントリーポイント、ビルド定義、設定、既存ドキュメントを読む。
- 既存の `docs/core/` は利用者向けマニュアルとして扱い、開発者向け構成資料と混同しない。
- README の記述を次の3種類に分類する。
  - 正確: 実装と一致している
  - 要修正: 実装と異なる、または誤解を招く
  - 要確認: 実装だけでは判断できない

### 2. 詳細ドキュメントの作成

- `docs/architecture/README.md` を目次として整備する。
- README の主要項目ごとに、必要な詳細 Markdown を作成する。
- 各文書では、役割・責務・主要ファイル・エントリーポイント・処理の流れ・関連機能との関係を、対象に必要な範囲で説明する。
- 実装に存在しない機能や、将来予定の機能を現行仕様として書かない。
- 既存の説明と重複する場合は、既存文書へのリンクを優先する。

### 3. ルート README の整理

- `README.ja.md` は概要を中心に簡潔にする。
- 各項目の末尾など、自然な位置から対応する詳細文書へリンクする。
- ディレクトリ一覧は実在する構成に合わせる。
- ビルドツールや配布形態などの変更されやすい説明は、現在の設定・処理を確認して記載する。
- `README.md` (英語版) と機能・構成の説明が食い違っていないか確認し、差分を報告する。英語版の変更は依頼範囲に含めず、必要性を報告すること。

### 4. 検証

- Markdown 内の相対リンクと参照先ファイルの存在を確認する。
- 説明に使った主要ファイルのパスが実在することを確認する。
- ドキュメント以外のファイルに変更がないことを確認する。
- lint / tsc はドキュメントのみの変更であれば実行不要。

## 成果物

1. `docs/architecture/README.md` と各詳細ドキュメント
2. 整理した `README.ja.md`
3. patch ファイル
4. 簡潔な作業レポート

## 作業レポートに含める内容

- 作成・更新したドキュメント
- README の記述で修正した点と、その根拠となる実装ファイル
- 正確性を確認できなかった点
- 英語版 README との不一致
- リンク確認結果
- ドキュメント以外を変更していないこと

---

このプロンプトの内容と `docs/conventions/root-readme.md` が矛盾する場合は、恒久ルールである `root-readme.md` を優先してください。
