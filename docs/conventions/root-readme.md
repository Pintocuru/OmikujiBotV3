# ルート README・構成ドキュメントのルール

## 1. 目的

ルートの `README.ja.md` はプロジェクト全体の入口とし、概要を簡潔に説明する。
各機能・ディレクトリの詳細な設計や実装説明は `docs/architecture/` に分けて記載する。

## 2. ドキュメントの役割

| 場所 | 役割 | 読者 |
| --- | --- | --- |
| `README.ja.md` | プロジェクトの概要、主要構成、ディレクトリ案内 | 利用者・開発者 |
| `README.md` | 英語版の概要。日本語版と内容を揃える | 英語圏の利用者・開発者 |
| `docs/architecture/` | 各機能・システムの責務、構造、処理の流れなど | 開発者 |
| `docs/core/` | 製品・機能の利用者向け説明書 | 利用者 |
| `docs/conventions/` | 開発・ドキュメント作成時の恒久ルール | 開発者・AIエージェント |

README に詳細を詰め込まず、必要な項目から対応する architecture 文書へリンクする。

## 3. architecture 文書の配置

- 開発者向けの構成・設計説明は `docs/architecture/` に置く。
- 原則として、README の主要項目ごとに Markdown ファイルを分ける。
- ファイル名は内容が分かる PascalCase または kebab-case とし、同じ階層では形式を統一する。
- 文書が増えた場合はサブディレクトリで分類してよい。
- 目次は `docs/architecture/README.md` に集約する。
- 利用者向けマニュアル(`docs/core/`)と開発者向け設計資料を混在させない。

## 4. 記載内容

各文書では、必要に応じて次を説明する。

1. **役割**: 何のために存在するか
2. **責務**: 何を担当し、何を担当しないか
3. **主要な配置**: 関連するディレクトリ・ファイル
4. **エントリーポイント**: 起動・初期化・登録の起点
5. **処理の流れ**: 主要コンポーネント間の呼び出しやデータの流れ
6. **関連機能との関係**: 依存先・連携先・境界
7. **ビルド・実行方法**: 構成を理解するうえで必要な場合のみ
8. **関連文書**: 詳細説明や利用者向けマニュアルへのリンク

すべての項目を機械的に埋める必要はない。対象に関係する内容だけを記載する。

## 5. 正確性のルール

- **実装を情報源とする**。ディレクトリ名やファイル名だけから役割を推測しない。
- 現在のコード・設定・ビルド定義を確認してから記述する。
- 実装で確認できた事実、設計意図、将来構想を区別する。
- 確認できない内容は推測で補わず「未確認」とする。
- 旧仕様・移行中の仕様を現行仕様として書かない。
- 例やコード片は現行コードと一致させる。不要なコード全文は転載しない。
- ファイルパスは実在を確認し、移動・改名時にリンク切れを確認する。
- 「常に」「すべて」「必ず」などの強い表現は、例外がないことを確認できた場合だけ使う。

## 6. ルート README の記述ルール

- プロジェクトの目的と全体像を最初に示す。
- 主要項目は「何をするものか」が一読で分かる短い説明にする。
- 実装詳細、細かな処理手順、内部型の説明は architecture 文書へ移す。
- ディレクトリ一覧は現在の実際の構成に合わせる。
- ビルドツール、起動コマンド、配布形態など変更されやすい情報は、設定ファイルと照合する。
- 日本語版と英語版で、構成・機能・対応範囲に食い違いを作らない。
- architecture 文書が未作成の項目に、存在しないリンクを設定しない。

## 7. 更新手順

1. `AGENTS.md` と `docs/conventions/` を読む。
2. README の各記述に対応する実装・設定・既存文書を確認する。
3. 必要な architecture 文書を作成・更新する。
4. `README.ja.md` の説明を短く整え、詳細文書へリンクする。
5. 英語版 README との内容差を確認し、差があれば報告する。
6. 追加・変更したファイル、根拠にした実装、未確認事項を報告する。

ドキュメント作業では、依頼がない限りアプリケーションコードや設定の挙動を変更しない。
