# UI内コンポーネント登録規約 — OmikujiBotV3

UI の内部で使う表示コンポーネント(例: KujibikiPanel の `omikuji` / `flower` / `tarot` / `faceCutout`)を、共通の仕組みで登録・管理するための基準。

- **第1部**: 恒久ルール(UI 全体に適用する)
- **第2部**: 今回の実装(KujibikiPanel への導入)の引き継ぎ。**実装完了後は第2部を削除してよい**

## 第1部 恒久ルール

### 1. 目的と適用範囲

- 表示コンポーネントが 10〜20 種に増えても、セット単位で追加・配布できるようにする。
- 登録・取得の仕組みは全 UI で共通にし、UI ごとの情報は UI ごとに独立して管理する。
- 現状は KujibikiPanel だけが対象。`StreamCounter`(8種・`layout` メタあり)など、`component` を持つ他の UI は将来この仕組みに移す。そのため、共通レジストリは特定 UI の型・メタ情報に依存しない。

### 2. 既存レジストリとの責務

| レジストリ                                                              | 責務                                                      | 扱い       |
| ----------------------------------------------------------------------- | --------------------------------------------------------- | ---------- |
| `src/ui/uiRegistry.ts`(`registerUi` / `getUiLoader` / `registerLayout`) | UI 本体・レイアウトの登録                                 | 変更しない |
| `src/editor/ui/uiEditorRegistry.ts`                                     | UI 全体のエディター・スロットエディター・プレビューの登録 | 変更しない |
| **UI内コンポーネントレジストリ(新規)**                                  | UI 内部の表示コンポーネントの登録                         | 本書の対象 |

3つは別物として扱い、責務を混ぜない。

### 3. 共通レジストリ

配置は `src/ui/common/uiComponentRegistry.ts` を推奨する(既存構成に合わせて変更してよい)。

#### 3.1 登録情報

| 項目        | 内容                                                                                           |
| ----------- | ---------------------------------------------------------------------------------------------- |
| ID          | コンポーネントを識別する文字列。**オブジェクトのキーがそのまま ID**(`id` プロパティは持たない) |
| `label`     | エディターで表示する名称。**日本語固定**(多言語化しない)                                       |
| `loader`    | Vue コンポーネントを読み込む非同期 Loader                                                      |
| UI 固有メタ | `isVisual` / `layout` など。**共通レジストリは解釈・加工しない**                               |

```ts
registerUiComponents('kujibikiPanel', {
  standard: {
    omikuji: { label: 'おみくじ', loader: () => import('./Omikuji.vue'), isVisual: false },
    flower: { label: 'フラワー占い', loader: () => import('./Flower.vue'), isVisual: false },
  },
})
```

- 第1引数は UI の種類、第2引数は「セット名 → コンポーネント群」。セット名は登録の単位であり、エラーメッセージや一覧表示のために使う。
- UI 固有メタは、ジェネリクスで型安全に保持する。**UI ごとに型付きの薄いラッパー**(例: `KujibikiPanelRegistry.ts`)を用意し、UI 側からはそのラッパーだけを使う。
- API の具体名・型は、既存コードとの整合を見て実装時に決める。

#### 3.2 ID の規則

- **形式**: `^[a-z][A-Za-z0-9]*$`(先頭小文字の camelCase)。登録時に検査し、外れたら登録エラーにする。ID は保存データの値になるため、空文字やスペース入りを防ぐ。
- **重複**:
  - 同一 UI 内では、セットをまたいだ ID の重複を**登録エラー**にする。
  - 異なる UI 間では、同じ ID を使ってよい。
  - 登録順による**上書きは認めない**。
- **再登録(HMR 対策)**: 同じ「UI + セット名」の再登録は、そのセット自身の分を置き換える。別セットに同じ ID があれば、重複としてエラーにする。

#### 3.3 型安全

- 保存データの ID は **`z.string()`**(列挙型にしない)。未同梱や将来追加の ID を、parse で書き換えずに保持するため。
- 登録側のタイポは、**既知 ID の定数配列(`as const`)と、そこから作る型**で防ぐ。定数配列は `src/types/ui` に置く。
- セットを追加するときは、定数配列への追記が必要。共通レジストリ本体は変更しない。

### 4. セット

#### 4.1 ディレクトリ構成

```text
src/ui/<UI名>/components/
├─ <セット名>/
│  ├─ register.ts      … そのセットの登録
│  └─ <コンポーネント>.vue
```

- 従来の `layouts/`(見た目のバリエーション用。`naming.md` §3)とは別の概念。UI 内の表示コンポーネントは `components/<セット名>/` に置く。
- セット名のディレクトリは camelCase とする。

#### 4.2 セットの扱い

- 配布パッケージのエントリは、**必要なセットの `register.ts` だけを明示的に import する**。
- 開発用の全部入り(`registerAll` / DevApp)と**エディターは、全セットを登録する**。
- 動的 import を書いただけでは、不要なセットが配布物から確実に除外されるとは限らない。**配布エントリの依存関係を、ビルド検証で確認する。**
- セットの追加で、共通レジストリ本体を変更しない。

### 5. 未登録コンポーネントの扱い(共通原則)

設定データの ID が、現在の登録に存在しない場合:

| 項目                   | 扱い                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| 設定データ             | **書き換えない・削除しない・別 ID へ自動変更しない**                                     |
| 代替表示               | 各 UI 側で実装する(共通レジストリには持たせない)                                         |
| 配信画面               | **無表示**にする                                                                         |
| 通知                   | `src/sdk/post/PostOneComme.ts` の `postSystemMessage` で、わんコメへ**一度だけ**通知する |
| エディターのプレビュー | **エラー表示**にする。未登録であることを明示する                                         |
| 復帰                   | 登録済みコンポーネントを選べば、通常の表示に戻る                                         |

- 通知の「一度だけ」の単位は、**ページ読み込みごと × UI × ID**。
- 通知のタイミングは、コメントが来たときではなく、**設定が決まった時点(先読み時)**。配信前に誤設定へ気づけるようにする。
- **未登録**と**読み込み失敗**は、原因が区別できるよう、通知の文面を分ける。

### 6. ビルド時検証

- **KujibikiPanel を登録するエントリは、`omikuji`(既定 ID)が登録されていること**。含まれない構成は**ビルドエラー**にする。
- 基本セットの同梱を義務づけるのではなく、「既定 ID が登録されていること」を検証する。
- KujibikiPanel を含まないパッケージ(例: StrawberryChocolate)は、検証の対象外とする。今後 KujibikiPanel を含むパッケージを作る場合は、自動的に対象になる。
- 開発用の全部入り構成でも検証できるようにする。
- ビルドは **Vite**。検証方法(Vite プラグインなど)は、`vite.config.ts` と `tools/viteConfig` の構成を確認して決める。
- 既定 ID `'omikuji'` は、Schema・検証・エディターに散らさず、1か所の定数にする。

## 第2部 今回の実装(KujibikiPanel への導入)

### 7. 実装範囲

- 今回は **KujibikiPanel のみ**。`StreamCounter`・`StreamCounterSchema`・`StreamCounterEditor.vue` は変更しない。
- 既存の 4 種の表示コンポーネントは、挙動を変えずに動くこと。
- 既存データとの互換性を維持する(既存の 4 つの ID はそのまま使える)。

### 8. セット分け・パッケージ構成

| セット     | コンポーネント       |
| ---------- | -------------------- |
| `standard` | `omikuji` / `flower` |
| `fortune`  | `tarot`              |
| `special`  | `faceCutout`         |

| 対象                              | 登録するセット               |
| --------------------------------- | ---------------------------- |
| OmikujiBot(全部入り)              | 全セット                     |
| エディター・DevApp・`registerAll` | 全セット                     |
| StrawberryChocolate               | **KujibikiPanel を入れない** |

### 9. 変更内容

#### 9.1 Schema(`src/types/ui/KujibikiPanelSchema.ts`)

- `component` を `z.string()` にする(既定 `'omikuji'`)。**空文字と文字列でない値だけ**を既定値に戻し、未知の文字列は保持する。
- `label` / `animation` / `displaySeconds` / `imagePath` / `iconSize` は共通設定のまま変更しない。ID によって Schema 全体を切り替える設計にはしない。
- `kujibikiComponents` / `KujibikiComponent` / `KujibikiComponentConfig` は、既知 ID の定数配列と型に置き換える。参照元を確認すること。

#### 9.2 Selector(`KujibikiPanelSelector.vue`)

- 固定の `componentMap` を廃止し、レジストリから Loader を取得して非同期に読み込む。
- **先読み**: `KujibikiPanel.vue` のマウント時と、`settings.component` の変更時に行う。最初のコメントを待たない。
- 読み込みが終わってから、登場アニメーションを開始する。
- 未登録・読み込み失敗は、§5 のとおり扱う。

#### 9.3 エディター(`KujibikiPanelEditor.vue`)

- 選択肢は、レジストリの登録情報から作る(表示名は `label`)。
- 現在の ID が未登録の場合は、**「未登録: xxx」という擬似エントリを選択肢の先頭に足す**。共有部品 `DisplayStyleSelector.vue` は変更せず、エディター側で対応する。
- 選択肢が 1 つ以下でも、未登録であることが見えなくならないようにする。
- `isVisual` は、エディター側でメタから取得して使う。**未登録の間は画像設定(`imagePath` / `iconSize`)を非表示**にする(値は保持する)。
- `src/maps/ui/KujibikiPanelMap.ts`(`kujibikiComponentMap`)は廃止する。

#### 9.4 ファイル移動

- `layouts/` の 4 つのコンポーネントを、`components/<セット名>/` へ移す。
- 移動に合わせて、import 元を更新する。

### 10. 実装時に確認・決めること

- `vite.config.ts` と `tools/viteConfig` を読み、ビルド検証プラグインの置き場所と方式を決める(モジュールグラフの検査、または登録内容を実行して確かめる方式。ただし `register.ts` の loader は遅延 import のため、実行しても `.vue` は読み込まれない)。
- `register.ts` の形式(副作用 import か、登録関数のエクスポートか)を決める。既存の `packages/_shared/commentBubble.ts` は関数形式。**ビルド検証が静的に追跡できること**を条件にする。
- `KujibikiPanel/layouts/*` を import している他のファイルがないか確認する。
- `src/types/ui` から消える型(`KujibikiComponent` など)の参照元を洗い出す。
- 通知文面(例: 「くじ引きの表示タイプ『tarot』は、このバージョンには含まれていません」「…の読み込みに失敗しました」)を決める。文面は変えてよい。
- エディターのプレビューで、`postSystemMessage` の通知を送るかを決める(推奨: 送らず、エラー表示のみ)。
- `docs/conventions/naming.md` §3 のディレクトリ表に、`components/<セット名>/`(UI 内の表示コンポーネント)の 1 行を追記する。
