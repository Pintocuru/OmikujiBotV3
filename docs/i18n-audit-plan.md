# src/editor i18n 未翻訳・翻訳漏れ調査計画

## 目的

`Pintocuru/OmikujiBotV3` の `src/editor` を対象に、既存の vue-i18n 対応を前提として、未翻訳・翻訳漏れ・ロケール依存処理の不足を調査する。コードの修正は行わず、検出結果と根拠を Markdown レポートに記録する。

## 調査前提

- 対象ブランチ: 調査開始時点の作業ブランチ（開始時に SHA を記録する）
- 対象コード: `src/editor/` 配下
- 翻訳集約: `src/i18n/editor/messageModules.ts`
- 翻訳ライブラリ: `vue-i18n`
- 対応ロケール: `ja` / `en`
- デフォルト・フォールバック: `ja`
- 翻訳ファイルは `messageModules.ts` の明示的 import / 登録により読み込まれる。翻訳ファイルを追加する場合は登録も必要だが、本調査では変更しない。
- `src/editor/maps` 等の表示用マップと翻訳メッセージ定義を混同しない。翻訳定義の実体は `src/i18n/editor/` 側も参照する。

## STEP 0 の確認結果

### 翻訳構造

`messageModules.ts` は各翻訳モジュールを namespace import し、`messageModules` オブジェクトに明示登録する構造。コメントにも、翻訳ファイル追加時は同ファイルへ登録すること、翻訳ではない Map は `src/editor/maps` に置くことが記載されている。

`src/editor/i18n.ts` は登録されたモジュールの export を走査し、各 export の `ja` / `en` オブジェクトをロケール別に deepMerge している。初期 locale と fallbackLocale はともに `ja`。

### リポジトリ規模

GitHub の `main` の再帰 tree で確認した時点の値:

- `src/editor` 配下: 262 files
- Git tree が返すファイルサイズ合計: 644,821 bytes（約 645 KB）
- 行数: 未計測。各ファイルを取得する際、行番号付き検索と併せて必要範囲を確認する。

### 静的解析環境

- `eslint` / `eslint-plugin-vue`: package.json に存在
- `vue-i18n`: dependencies に存在
- `@intlify/eslint-plugin-vue-i18n`: package.json に存在しない
- `vue-i18n-extract`: package.json に存在しない
- `eslint.config.ts`: 現状、vue-i18n 専用 plugin / rule の設定なし
- package script: `npm run lint` は `eslint src`

GitHub API だけではリポジトリ内コマンドを実行できない。ローカル checkout 等の実行環境が利用可能な担当者は、既存 lockfile と package manager を確認してからツールの利用可否を検証する。依存追加・lockfile変更は禁止。実行できなければ「未実行」と明記し、ソース解析で補う。実行していない解析を実行済みと記載しない。

## 調査項目

1. **Missing key**: `t()` / `$t()` / `i18n.t()` 等が参照するキーが、実際に統合される翻訳定義に存在するか。
2. **ハードコード文字列**: UI に表示される日本語・英語が翻訳関数を通っていない箇所。特に `aria-label` / `placeholder` / `title` / `alt` / `confirm()` / `alert()` / toast / エラー文言を重点確認。
3. **翻訳値の不足**: キーは存在するが、英語側が未定義・空文字・日本語のまま等。製品名・固有名詞・仕様上意図された表記は自動的に未翻訳扱いせず、判断根拠を記録。
4. **動的キー**: template literal、文字列連結、変数経由など静的に列挙できないキー。候補キー集合との照合を行い、網羅性が保証できなければ「要確認」。
5. **ロケール対応**: 複数形、日付、時刻、数値、通貨、単位等について、固定文字列・固定フォーマットが locale に依存する箇所。

## バッチ分割

原則として機能ディレクトリ単位、1バッチ5〜10ファイルを目安に分割する。大きなファイルや密接な依存がある場合はファイル数を減らす。開始時に最新 tree を取得し、各バッチの**対象ファイルを具体的なパスで確定**して progress.md に記録する。下記は初期の目安であり、実際のファイル一覧を見て再調整する。

|---|---|---:|

| 03–09 | `src/editor/assets/` | 7〜9ずつ |
| 10–12 | `src/editor/content/` | 8〜9ずつ |

## 1バッチの作業手順

1. `progress.md` を読み、対象バッチ・対象ファイル・調査基準・既処理ファイルを確認。
2. 対象ファイルの現行内容を取得し、行番号を確定。ファイル全文の貼り付けは避け、検索結果と該当周辺だけを読む。
3. 翻訳定義と `messageModules.ts` の登録状況を照合。必要に応じて呼び出し元・定義元を対象外ファイルから最小限参照する。
4. 利用可能な静的解析を実行。コマンド、対象、終了コード、実行できなかった理由を記録。
5. 誤検出を除外しきれない項目は「要確認」とし、確度（高/中/低）を付ける。
6. `reports/batch-XX.md` を新規作成し、検出箇所を表で記録。該当なしの場合も、調査範囲・実施内容・該当なしを記録。
7. 担当バッチの結果を coordinator に渡す。progress.md は coordinator のみが更新し、並列作業時の更新競合を防ぐ。
8. 1バッチ終了後に停止し、処理ファイル数・検出件数・残バッチ数を報告。次バッチへ進まない。

## レポート形式

`reports/batch-XX.md` に以下を記録する。

- 調査対象ブランチ / commit SHA
- 対象ファイル一覧
- 静的解析ツール・実行コマンド・実行結果（未実行の場合は理由）
- 検出一覧

| ファイルパス:行 | 該当コード（短く） | 問題の種類 | 推奨修正 | 確度 |
|---|---|---|---|---|

問題の種類は `missing key` / `hardcoded string` / `empty or untranslated value` / `dynamic key` / `locale formatting` / `要確認` を使用する。複数行にまたがる場合は開始行を示す。コード引用は必要最小限にする。

## 進捗ファイル

`reports/i18n-audit/progress.md` に以下を保持する。

- 調査対象ブランチ / commit SHA
- 完了バッチ / 未完了バッチ
- バッチごとの対象ファイル
- 処理済みファイル一覧
- 問題種別ごとの検出件数（確定 / 要確認を分ける）
- 静的解析の実行状況
- 次に再開するバッチ

会話や担当者が変わっても、このファイルと各 batch レポートだけで再開できる状態にする。

## 並列エージェント運用

- 複数エージェントに依頼する場合、各エージェントには重複しないバッチと同一の調査プロンプトを渡す。
- 各エージェントは割り当てられた `batch-XX.md` のみ作成・更新する。
- `progress.md` は coordinator だけが更新する。
- 同じバッチを複数エージェントに割り当てない。
- 翻訳定義の共有ファイルを変更しない。調査中に必要な参照は読み取りのみ。
- レポートの統合時に重複検出を整理するが、異なる発生箇所は消さない。

## 禁止事項

- `src/editor`、`src/i18n`、設定ファイル等のコード変更
- 翻訳キーの追加・削除・修正
- 依存パッケージや lockfile の変更
- 調査結果の推測による補完
- 根拠のない「未翻訳」判定
- バッチ途中での `AGENTS.md` 更新

## 最終工程

全バッチ完了後、coordinator が結果を横断集計し、重複・誤検出・要確認を整理する。最終サマリのみ `AGENTS.md` に追記する。個別レポートと progress.md は保持する。最終サマリには件数、問題種別ごとの傾向、優先度の高い箇所、未確定事項、静的解析の実行可否を含める。
